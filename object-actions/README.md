# 企业对象、关系、动作 Schema 与 README 的端到端对照

## 结论

在这组口径已知、动作会复用的企业任务里，我会选对象、关系、动作 Schema 接受控函数。严格接口复验中，按域查 README 与图查找同样能准确定位意图、正确返回。图查找平均少用约 60% 输入 token，端到端中位时间由 0.858 秒降至 0.733 秒，按 API 名义费率估算请求成本少约 29%。在已明确限定范围的首次探索任务中，README 加自由 SQL 也是实用方案。首轮两组 SQL 的最终返回均是 40/40。准确率方面，本实验未观察到 Schema 的优势。

## 该方案是什么

这里用类型化的企业对象、关系和动作定义业务。查询先在 24 个域的目录里做英文分词和同义词命中，定位对象候选，沿显式边扩展两步，再披露最多四个动作签名。模型挑业务动作、域和参数，运行时调用预先实现的读写函数。订单和工单数据仍在底表。独立 Python 参考逻辑按业务规则重算数值和应有的状态变更。严格工具模式的第二轮通过服务端 JSON Schema 约束参数。

- **最接近的企业项目是 Palantir Foundry。** 对象后端定义对象、关系、动作和读服务。OSDK 暴露关系遍历、服务端查询函数和动作。AIP Analyst 可搜索对象类型的名称、别名与描述，再转成对象集合、应用动作或在对象集上使用 SQL。具体实际走哪条路取决于已启用的工具和权限。 [Foundry 对象后端](https://www.palantir.com/docs/foundry/object-backend/overview) · [OSDK](https://palantir.github.io/osdk-ts/concepts/ontology) · [AIP Analyst 能力](https://www.palantir.com/docs/foundry/aip-analyst/capabilities)
- **可借的公开实现与评估方法。** MetricFlow 用 YAML 语义模型、实体键和指标口径生成查询，适合参考读侧口径封装。Berkeley Function Calling Leaderboard 为工具选择和参数质量提供样例。τ-bench 用最终数据库状态检查动作是否正确，适合参考写入判分。 [MetricFlow 源码](https://github.com/dbt-labs/metricflow) · [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) · [τ-bench](https://arxiv.org/abs/2406.12045)

## 规模、任务与判分

20 道题，每题每组两次。任务含单域数数、CRM 到订单的筛选、支付与历史制度、双域回款差、缺关系、获批和未获批的工单写入。24 个业务域、216 张源资产说明及一份工单规则。全文组均值 21,008 输入 token，含动作手册和提示词。SQLite 保存约 7,600–57,000 行合成底表。最终值用四份快照验算，写入检查整个练习表变化。两个意图字段和业务参数均正确才算意图命中，另对最终实际回执独立判分。

时间从本地找到材料开始，到模型返回且首个预热快照得出回执。包括 API 网络和队列等待，在同轮随机交错提交，最多八并发。请求只生成一次决策，最终返回是结构化工具回执。没有单独生成自然语言答案。每列均为样本内描述值。价格按服务方公开较高时段费率和 API 实报缓存命中、未命中及输出 token 估算。较低时段费率为表中一半。未计数据库、运维、建模与维护成本。 [DeepSeek 模型和价格](https://api-docs.deepseek.com/quick_start/pricing/)

## 首轮四个方案

| 路径 | 意图正确 | 实际回执正确 | 中位数 / P90 | 平均输入 token | 40 次 API 估算美元 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全文 README → 自由 SQL | 40/40 | 40/40 | 0.962 / 1.342 s | 21,008 | 0.02399 |
| 按域 README → 自由 SQL | 37/40 | 40/40 | 0.886 / 1.302 s | 1,511 | 0.01315 |
| 按域 README → 函数 | 39/40 | 39/40 | 0.785 / 1.108 s | 1,481 | 0.01069 |
| 对象路径 → 函数 | 36/40 | 36/40 | 0.672 / 1.048 s | 340 | 0.00456 |

按域 SQL 有三次意图字段不准。例如把域填成 `elm-bridge`。被拒绝的写入碰巧给出正确结果。图组四个错误都找到正确操作和业务域，失败发生在模型把域名同时写入顶层及参数对象，执行函数拒绝非法结构。README 函数组有一次同类失败。首轮这是端到端真实失败。

## 同一批严格函数的复验

| 路径 | 意图正确 | 实际回执正确 | 中位数 / P90 | 低于 1 秒 | 平均输入 / 输出 token | 40 次 API 估算美元 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 按域 README → 同一套函数 | 40/40 | 40/40 | 0.858 / 1.191 s | 28/40 | 2,955 / 53.4 | 0.01303 |
| 对象路径 → 同一套函数 | 40/40 | 40/40 | 0.733 / 1.103 s | 32/40 | 1,180 / 53.55 | 0.00928 |

首轮和复验分开记录。严格调用的输入含工具 Schema。复验中对照组读本域资料并提供八个动作，图组通过本地检索提供最多四个动作。测到的是按需披露整套做法的收益。更细的消融还可以让按域 README 也按需提供四个函数，以定位图拓扑对选择的独立贡献。严格接口只接收合法的参数形状，仍由动作实现检查权限和业务逻辑。四个写题的两次执行在各组都符合预期。没有组在本实验中越权改动。 [严格调用文档](https://api-docs.deepseek.com/guides/tool_calls/)

## 用一题解释差异

第 13 题让智能体算 Grove 与 Juniper 的净回款差，两边都要按各笔订单日期应用历史财务制度。全文组写出两个子查询，分别汇总已结算退款，再相减。图组先取到财务制度和订单对象，展开到退款对象，工具回包调用 `collections_delta(brand="Grove", other_brand="Juniper")`。两组首个快照都返回 −6,273 分。复验里受控函数按预先封装规则计算，模型只决定动作和参数。

四道写题是模拟工单，不同的审批和角色在服务端得到不同回执。使用者没有主管角色时，即使发来格式正确的动作请求，执行也不改工单。该控制可以由文档加同一个函数复用。

## 外推边界与复验

20 题来自八种预定义动作，题面写明域名，检索用英文词与人工同义词。只测一个模型、单次决策、已有动作和合成目录。这些对照未测企业千域、中文分词、开放式新任务、跨服务网络、长会话和维护成本。对于是否采用，下一步用真实任务样本评估命名歧义、未建模新需求、修改口径后的回归，以及实际的建模和运行费用。

