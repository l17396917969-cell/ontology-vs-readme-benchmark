# 实测 · 两百多份说明，智能体在哪里出错？

## 先看结果

同一个 DeepSeek Flash API 模型，两套题合计 40 道，8 类首轮模板加 4 类新模板，248 次独立调用。模拟企业有 24 个业务域、216 张资产说明、192 张 SQLite 业务表。每域有关系底表、支付明细、客服、分析宽表及一份财务制度说明。把资产卡放在同一份 Markdown，约 20.6k 输入 token。数据库始终在本地。全文组两轮均全对。

**首轮 16 题**　题不变，模型只看本域 9 张说明，或在企业目录的 216 张中检索。

| 输入策略 | 只给本域资料 | 面对企业目录 | 企业目录参考材料找齐 | 企业目录平均输入 token |
| --- | ---: | ---: | ---: | ---: |
| 整份 README | 16/16 | 16/16 | 16/16 | 20,578 |
| BM25 搜索，取 6 张 | 13/16 | 8/16 | 10/16 | 779 |
| 从一个搜索命中沿显式关系，取 6 张 | 14/16 | 15/16 | 14/16 | 717 |
| 直接给参考材料 | 16/16 | 16/16 | 16/16 | 453 |

**第二轮 24 道新题**　企业目录规模固定。每类 6 题，其中两域题需要分别在两个域查账。

| 输入策略 | 总正确 | 单域客服 | 历史口径 | 两域差额 | 合作伙伴身份缺失 | 平均输入 token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 整份 README | 24/24 | 6/6 | 6/6 | 6/6 | 6/6 | 20,588 |
| BM25 搜索，取 6 张 | 6/24 | 0/6 | 0/6 | 0/6 | 6/6 | 811 |
| 单入口关系导航，取 6 张 | 12/24 | 6/6 | 0/6 | 0/6 | 6/6 | 729 |
| 按题面域名定位，取 9 或 18 张 | 24/24 | 6/6 | 6/6 | 6/6 | 6/6 | 1,204 |
| 事后诊断，给齐参考材料并补到 6 张 | 23/24 | 6/6 | 6/6 | 6/6 | 5/6 | 762 |

表中报的是模型请求返回的输入 token，取整。第二轮按域路由输入约为全文的 1/17。路由依赖题里显式出现域名，允许更多卡片，给了文本一套实用基线。参考材料诊断可见出题时预定的参考集合，不能作为部署方案。

**行数单独改。** 相同 SQL 在四个快照执行。每域 24 或 240 笔订单，各用两个种子。全库实际行数分别为 7,716、7,601、56,334 和 56,948。每道可答题须四次执行都对才算通过。C11 的关键词方案把不该计入的工时算了进来，只在第一份快照露出错误，另外三份恰好相等。使用单一快照会误判这条 SQL。实验没有比较数据库执行性能，也没有把业务明细行放进提示词。

## 典型错误与干预

| 题号 | 原始错误 | 具体证据 |
| --- | --- | --- |
| 首轮 A07 | 关键词结果被多个域的同名财务制度占满 | 前六条全是制度，漏掉 Aster 订单和退款表。模型猜了一个不存在的表名。关系检索从制度扩展到下游资产，四次 SQL 执行都正确。 |
| 第二轮 C12 | 同域顺着边找到了订单和客户，没把支付说明带进 6 张内 | SQL 猜字段是 `amount`，实际为 `cents`，还缺已结算状态。相同预算换成含支付的参考资料后，该类 6 题全对。 |
| 第二轮 C13 | 从一个入口展开，6 张说明都来自 Cedar | 生成的 SQL 两边都用 Cedar 的表，第一份快照输出 0，参考答案 −11,750 分。给同样六张但两边各三张，六道两域题都恢复正确。该结果只能说明本次单入口策略的边界。 |
| 首轮 A08 | 无合作伙伴身份映射，依旧返回 0% | 生成 SQL 把 CRM 等级当成合作伙伴分类。已知材料也没有保证消除同类错误，第二轮六张参考资料诊断仍有一次误答。 |

## 本体在哪一步提供价值

1. **让关系能被程序使用。** 本实验给 Markdown 与机器可读目录同样的说明和链接。从 Markdown 重新解析显式链接后，首轮 32 个题目与范围组合的导航结果均逐项相同，模型收到的文字也相同。结构组只使用关系目标做导航，未调用类型推理。能用一个目录或 Markdown 做成同样可查询的结构时，这部分价值可以共享。
2. **给业务概念一个稳定的查询入口。** 另做了一个本地工具演示。受控净回款函数锁定订单主键、已结算退款、旧新版制度生效日和过滤方式。模型生成的 0% 可正常执行。用同一指标意图手动调用只接受已登记指标的工具，得到 `unsupported_metric`。受支持的净回款在 24 域 × 4 快照 × 2 种过滤下 192 项核对通过，另有 96 次不支持指标核对。这里测试的是写好的查询工具。README、语义层或本体都可以接入它。 [实现](metric_demo.py) · [回显](metric-demo.json)
3. **按风险决定在哪层投资。** 在文档充分、可按域找齐且只读的条件下，全文或按需查 README 已是可行基线。经常跨多个源、业务口径反复修改，或结果后续要触发操作时，预先登记并验证关键关系和指标值得单独比较。实际投资回报还要记录新问题编写时间、改口径后的回归、维护工时、拒答和错误决策成本。此次未量化这些指标。

“几百份能不能塞进上下文”要看这些文件的总 token、模型窗口、其余输入和输出的预算。这里仅证明 216 张短说明在该配置下可以，并在这些题上答对。真实企业 SQL 基准需要同时找表、连接键、业务知识与查询分解。论文中的更难任务说明这份合成成绩不能直接外推。 [BEAVER §5](https://arxiv.org/html/2409.02038v3#S5) · [Spider 2.0](https://proceedings.iclr.cc/paper_files/paper/2025/file/46c10f6c8ea5aa6f267bcdabcb123f97-Paper-Conference.pdf) · [一手调研](../research.md)

## 复现

在本目录执行。Python 3.11 和现有 `openai` SDK。已有原始回包时以下命令均可离线运行。

```sh
PYTHONDONTWRITEBYTECODE=1 python3 run.py prepare
PYTHONDONTWRITEBYTECODE=1 python3 run.py grade
PYTHONDONTWRITEBYTECODE=1 python3 follow_up.py
PYTHONDONTWRITEBYTECODE=1 python3 metric_demo.py
```

调用新模型时把证据目录复制一份并保留原始回包。首轮可用 `run.py run` 调用缺少结果的组合，第二轮用 `follow_up.py --run` 主动调用缺失组合。凭证只读 `DEEPSEEK_API_KEY` 环境变量。API 回报模型名 `deepseek-flash`，初始固定 temperature 0、禁用 thinking、每次 1,600 输出 token 预算。无历史会话，模型只提交 SQL 或拒答。选择单次样本作为探索性估计，模型别名未固定后端快照。
